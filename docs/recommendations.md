# 每日菜谱推荐

推荐算法版本为 `personal-meal-v3`。首页、午晚餐、心情、明日菜单、周菜单、盲盒、Web 转盘候选、站内助手、MCP 与 Agent REST 使用同一推荐核心。

## 选菜与隐藏评分

先过滤当前用户不可见、停用、过敏与明确忌口冲突、请求排除食材/菜品，以及不满足餐次、必含食材、难度和请求时长的菜。未知耗时不能通过明确的时长上限。过敏、忌口和排除条件不能在无候选时自动取消；`ignore_preferences` 也不能绕过这些条件。

必含食材和家中库存使用真实原料身份及同义词；过敏排除另做分类展开。例如“西红柿”和“番茄”可互换，生抽库存不等于豆腐库存；“贝类”“坚果”等预置分类可排除对应常见原料。词表不是对未知复合配料的完整识别，菜谱原料应持续核对。

每道候选菜的六项得分均为 0–100，最终权重为个人喜好 35%、当餐匹配 20%、近期新鲜感 15%、做饭便利 15%、整餐搭配 10%、资料完整度 5%。个人喜好将历史相似菜的正负证据加入先验，再采用 5 个先验样本与同一道菜的实际评价做平滑。真实评价按 45 天半衰期衰减；收藏与私房菜是有限先验，不把整分乘以来源倍数。已吃、评价及反馈变更后可以从原始证据重算 `user_dish_affinities`，缓存不是原始事实。

星级优先于同一次记录的情绪评价，未评价记餐只产生弱证据；正负证据分别影响菜和画像。未来旧记录不参与当前实际食用画像，不自动推断或批量迁移历史含义不清的记录。新写入的未来餐次进入独立计划。

多道菜逐道重排，考虑主食材、菜品角色、做法和辣度，并按与任意已选菜的最大内容相似度抑制近似重复，避免重复惩罚被整餐平均值稀释。已有计划参与占位与搭配，同日尽量不重复，周内优先不重复。菜谱结构来自原料及可识别特征，未知保留未知，不把历史“素菜”标签当作严格素食依据。

分数不代表概率、好吃程度或营养评价。用户界面只展示主要推荐理由；旧接口的 `score` 保留供现有客户端兼容。

## 从历史菜谱寻找相似因子

v2 将历史压缩成独立的口味、菜系与食材占比，新菜主要依赖最大单项权重。v3 在请求内建立菜谱内容向量，用带平滑 IDF 的加权余弦相似度比较完整菜谱：食材身份权重最高，烹饪方法、较弱的蛋白食材类别与口味次之，菜系和菜品角色只作辅助。食材先去重并归一化真实同义词；调料不会因为普遍出现而成为主要推荐依据。仅有相同菜系或口味，不构成历史相似菜证据。

食材、蛋白类别与口味各自按不同特征数量的平方根归一化，再施加 IDF，避免长配料表淹没烹饪方法。六种食材相同但从炒改为炖的回归样例，余弦相似度约为 0.710；完全相同的归一化食材与做法仍接近 1。这些数值是固定测试样例的内容相似度，不是用户喜欢的概率。

历史来源包括当前用户的实际记餐与评价、收藏，以及明确不喜欢。每道历史菜的影响随证据强度收缩，正负邻居分别取有限数量，避免大量重复记餐压倒其他偏好。收藏可为没有记餐的新用户提供较弱的相似菜线索；未评价记餐只有弱支持。明确差评不能被该菜的收藏转成正向来源，候选菜自身的差评也不会得到正向相似加成。跳过、曝光、查看和未来计划不当作满意度。

例如，喜欢“番茄炒蛋”后，“西红柿炒鸡蛋”能获得食材组合与做法的支持，“番茄炖豆腐”保留熟悉食材又有变化；仅同属清淡口味的无关菜不会获得这条历史相似加分。这是内容与个人证据的混合推荐，不是跨用户协同过滤，也不生成新菜谱。

## 有依据的新菜探索

新鲜感同时考虑菜品 ID 与内容。近期吃过的高度相似菜、历史喜欢菜的近似复制品会降低新鲜感；有正向历史支持、又有食材或做法差异的新菜可获得有限加分。冷启动时回退到显式偏好、餐次、便利程度和资料完整度。

三道及以上的请求在最后一个位置尝试一次探索；一至两道的请求以约 20% 概率在第一个位置尝试。只有存在合格候选时才发生替换，最多一次。探索候选必须满足原有全部硬约束、没有吃过或收藏、没有明确差评、有足够的好评或收藏相似来源，且总分距当前最优不超过 6 分。未评分的重复记餐只能影响弱相关性，不能累积成这项探索资格。近似复制品、负向支持过强或与已选菜过于相似的菜不会进入探索。候选按相关性与内容差异排序，不再均匀随机抽取。

`diversity=false` 关闭探索、内容新颖性加减分和整餐搭配调整，仍保留历史相似偏好与原有按用餐日期计算的新鲜感。推荐理由来自真实共同食材与做法，低置信证据不会被描述为明确喜欢。

内容向量与历史支持在一个推荐上下文中构建，周菜单可复用。快照键包含历史模型指纹；即使修改的是本次候选之外的历史菜谱，也会使旧推荐失效。算法版本升级同步使旧日推荐和周菜单缓存失效，无需新增数据库表。

## 开源方案与验证

通过 ego 浏览器查阅的方案：

| 方案 | 可借鉴能力 | 本项目取舍 |
| --- | --- | --- |
| [Gorse](https://github.com/gorse-io/gorse) | Go 推荐服务、多路召回、基于内容标签的相似项、反馈重排 | 参考 [Item-to-Item](https://gorse.io/docs/concepts/recommenders/item-to-item.html) 的稀有特征加权与历史邻居思路，结合食材语义实现本地评分；未部署 Gorse 服务 |
| [LightFM](https://github.com/lyst/lightfm) | 将用户和物品元数据融入矩阵分解，支持新物品泛化 | 需要 Python 训练流程和足够交互数据，作为后续模型实验候选 |
| [Recommenders](https://github.com/recommenders-team/recommenders) | 算法范例、数据切分、离线评估与模型选型 | 参考评估流程；当前没有引入其运行时依赖 |

当前内置菜谱规模约 100 道，采用请求内内容模型可以直接利用已有数据，不增加训练服务、向量数据库或模型 API 调用。上述方法有公开实现依据，本次评分公式和领域特征为本项目实现，没有宣称已接入外部框架。

行为回归覆盖历史食材组合迁移、不同用户排序、仅收藏用户、负反馈与撤销、删除历史重算、历史菜谱编辑失效、近似重复、探索门槛和过敏过滤。运行 `go test ./...`、`go vet ./...` 与 `node --test scripts/tests/recommendations.test.cjs`；基准运行 `go test ./internal/services -run '^$' -bench BenchmarkRecommendationV3ReusedContext -benchmem`。

这些测试验证规则与性能，不代表线上采纳率提升。后续效果评估应按时间划分历史训练段与未来评价段，比较 Recall@K、NDCG@K、推荐内容重复率和新菜覆盖；线上以真实曝光归因后的采纳率与明确差评率为准。不能把随机未观察菜当作用户不喜欢，也不能将测试段反馈混入画像。

## 每日稳定性与反馈

推荐按北京时间的日期、餐次、请求条件及用户证据生成轻量快照，只存菜 ID、评分分项和理由。普通重载复用结果；当前可见性、启用、禁忌和约束会重新核验。不同设备与来源可以复用同一用户的快照；同时首次请求通过用户行锁收敛。

返回新增 `recommendation_id`、`session_id`、`served_for_date`、`meal_type`、`algorithm_version`，每项增加 `item_id`。连续换菜传 `session_id`、`refresh=true`，已实际展示/跳过的菜在会话内排除；显式 `exclude_dish_ids` 永不被清空。快照保留 30 天，按用户限量清理过期项。

返回候选不等于真实曝光。页面可见才发送 `impression`；预取菜不直接计曝光。`skip` 是换一个，不降低长期偏好；`not_today` 当天冷却；`dislike` 是明确不喜欢，`undo_dislike` 撤销。旧 `reject` 仅保留短期弱信号。归因反馈校验用户与推荐菜的关系，`request_key` 防重，事件与幂等凭据同事务保存。通用 `/behavior` 不能绕过归因校验。

采纳率按去重后的真实曝光项及对应采纳项计算；缺少推荐关联的历史事件不纳入新指标。加入计划时由服务端记录采纳，客户端无需另发 `accept`。

## 计划与真实食用

复用 `health_plan_items` 管理个人已确认菜单。新增 `source` 和 `recommendation_id`，保留健康报告原接口。计划与购物条目同事务写入，添加幂等、整餐替换原子提交。撤销计划时仍有实际记录的采购条目保留，删除实际记录时仍有计划的条目也保留。

| 接口 | 用途 |
| --- | --- |
| `GET /api/meal-plans?date_from=…&date_to=…` | 查询已确认菜单 |
| `POST /api/meal-plans` | 添加一道计划菜 |
| `PUT /api/meal-plans` | 原子替换整餐，空 `dish_ids` 清空 |
| `DELETE /api/meal-plans/:id` | 撤销一道计划菜 |
| `POST /api/recommendation-feedback` | 可靠归因反馈 |

添加输入：`dish_id, meal_date, meal_type, recommendation_id?`。替换输入：`meal_date, meal_type, dish_ids, recommendation_ids?`，其中 `recommendation_ids` 以菜 ID 为键、推荐 ID 为值。手动选菜可不关联推荐；明确选用时允许改餐次或有效日期，服务端重新核验实际计划的权限和忌口。

计划允许今天起七天内、早餐/午餐/晚餐，每餐最多 10 道。计划不会写入 `meal_records`，实际吃过再记餐。旧站内 `/records`、批量接口和 Agent REST 的未来写入兼容转计划，并返回 `planned`；实际 `created` 只含真实记录。Agent 需要 `plan:write` 才能写未来计划。旧 MCP `log_meal` 的未来日期同样转计划，返回 `planned=true`、`plan_id`，不返回真实 `record_id`。

Agent 建议收件箱采纳也进入计划，保留响应的 `created` 数组，新增 `planned=true`。已有独立确认计划在周菜单重生成时保留。

## 第三方 MCP 与发布

Agent API 版本为 `2.1`，既有推荐参数和工具名保留，新增契约见 [Agent 接口](agent-api.md)。工具注册表同时生成 MCP、Function Calling 和 OpenAPI 定义，所有数据仍绑定令牌所属用户。

新增 `user_dish_affinities`、`recommendation_snapshots`、`recommendation_feedbacks`，并为 `health_plan_items` 添加两列。启动、离线迁移与账号注销共享对应模型；上线需要先备份并在隔离数据库验证迁移，再运行一次独立迁移，正常 API 保持 `DB_AUTO_MIGRATE=false`。不回写历史评分或历史用餐日期。
