# 标准食物目录：核验、导入与撤下

状态：目录基础能力已实现，未预装真实营养数据。首批内容的授权、中文映射和人工核验仍需完成。这里的“核验”记录内容提供者给出的核验人和日期，不表示医学认证，也不由程序自动证明许可有效。

## 数据准备

输入为 UTF-8 JSON 数组，每批 1–1000 项、文件最多 16 MiB。每项使用以下字段，未知字段或数组后的额外 JSON 会被拒绝。

| 字段 | 必填与口径 |
| --- | --- |
| `name` | 1–100 字的食物名称 |
| `aliases` | 最多 20 个别名，每个 1–100 字；搜索按名称和别名匹配 |
| `basis_unit` | `g` 或 `ml`，营养值统一为每 100 单位 |
| `food_state` | `as_sold`、`ready_to_eat`、`raw`、`cooked`，须与数据来源一致 |
| `edible_basis` | 固定为 `edible_portion`，表示已去除不可食部分 |
| `nutrients` | 六项可选数值，至少一项已知；未知用 `null` 或省略，不得填零 |
| `provenance` | 下列完整来源信息 |
| `portions` | 可选，最多20项有核验依据的标准份量；不提供时只能直接填克/毫升 |

营养字段：`energy_kcal`（千卡）、`protein_g`、`carbohydrate_g`、`fat_g`、`fiber_g`（克）、`sodium_mg`（毫克）。源数据若是千焦、每份或干重，需在内容核验阶段确认转换依据，不能只改字段名。系统不推断生熟、克与毫升、带骨与可食部分之间的换算，标准碗/个的用量仅使用内容核验阶段提供的对应数据。

来源字段：

| `provenance` 字段 | 要求 |
| --- | --- |
| `dataset`、`version`、`record_id` | 各 1–80 字，不带首尾空白；三者共同标识不可变的来源条目 |
| `url` | 原始来源 HTTPS 链接，不含用户名密码，最多 500 字节 |
| `license` | 实际许可或授权依据，最多 500 字 |
| `reviewed_by` | 实际核验人，最多 100 字 |
| `reviewed_at` | `YYYY-MM-DD`，不得晚于北京时间今天 |

核验时检查食物名称/别名是否准确、状态与可食口径是否一致、六项营养单位是否正确、缺失与真实零值是否区分，并保留授权证据。测试里的虚构数据仅用于自动化回归，不能作为线上食物导入。

## 有来源的标准份量

每项 `portions` 包含 `key`（该食物内唯一、1–40字节）、`label`（如来源定义的“一平碗”，1–60字）、`amount`（0.01–10000，单位沿用父食物的 `basis_unit`）、`reference`（实际换算来源/测量依据，1–500字）。份量必须对应同一生熟状态和可食部分；其授权与核验记录沿用条目的 `provenance`。没有依据时省略整个字段，不能填写通用默认碗重。

日记使用 `nutrition_portion_key` 与 `nutrition_portion_count`，并继续提交所选个人食物 ID、基准单位和状态。数量大于0且不超过100，可填0.5；不得同时提交 `nutrition_amount`。后端从个人副本读取份量系数，计算总用量（不超过10000g/ml），忽略客户端声称的称量属性并固定标为估算。历史快照的 `standard_portion` 保存份量名称、数量、系数与换算依据，未知营养仍为空。

当前标准份量入口用于直接记餐；混合配方原料继续填写实际克重/毫升。切换食物或改回直接填克重时清空旧份量输入。校验、导入与重新采纳规则均与营养数据版本一致：改变份量系数同样必须发布新来源版本。

## 校验与导入

以下命令从 `backend` 目录执行，文件路径替换为已核验的数据文件。

```sh
go run ./cmd/nutritioncatalog -file /path/to/reviewed-foods.json
```

默认只校验文件，不打开数据库。`-migrate` 必须同时有 `-apply`。正常部署先通过独立迁移流程升级全部应用模型；该命令的 `-migrate` 只创建/升级公共目录表，不能代替应用迁移。

本地 SQLite：

```sh
go run ./cmd/nutritioncatalog -file /path/to/reviewed-foods.json -sqlite /path/to/app.db -apply
```

生产/预发布 MySQL 使用环境中已安全配置的 `MYSQL_DSN`，不要在命令行粘贴凭据：

```sh
go run ./cmd/nutritioncatalog -file /path/to/reviewed-foods.json -mysql -apply
```

必须且只能选择一个目标数据库。首次部署前备份并在预发布演练。整批事务导入，遇到同一来源标识/版本/编号的内容冲突则整批回滚；同一内容重复导入不重复新增，也不重新启用已撤下的条目。修正营养数据或来源元数据必须使用新 `version`，不能原地改旧版本。

## 查找、采纳与历史

登录用户通过 `GET /api/health/catalog?q=名称或别名&state=raw` 查找启用条目，最多返回 50 项；缩小搜索词和状态可细化结果。`POST /api/health/catalog/:id/adopt` 将条目复制到本人的食物列表，重复采纳返回同一副本。包装标签、标准食物副本与配方合计最多 300 项。

Web 与小程序在记餐表单的“查找标准食物”展示来源、许可与核验信息。采纳后仍需填写个人实际可食摄入量，单位和状态必须一致。有标准份量时可选择数量，报告会标为估算并展示换算依据。副本只读，可从自己的食物列表移除。目录版本更新不会静默替换个人副本；用户需要自行选择新版本。

标准食物可直接记餐，也可作为无需加热且全部原料保留的混合配方原料。历史快照保存原目录版本及配方逐原料来源；报告能查看来源依据。标准食物直接计算使用 `catalog-per100-v1`，混合配方使用 `retained-mixture-v1`。覆盖门槛及星期配对规则沿用健康报告，未知营养仍为未知。

## 撤下与更正

```sh
go run ./cmd/nutritioncatalog -mysql -withdraw 123 -apply
```

SQLite 则用 `-sqlite /path/to/app.db` 替换 `-mysql`。ID 必须来自目标库中的目录条目；不存在的 ID 返回失败，重复撤下已存在条目可安全重试。撤下和采纳锁定同一来源行，完成撤下后不再允许新的采纳。

撤下会停止搜索展示和新采纳，**不会删除或停用已有个人副本、配方及历史记录**。已有副本仍能记餐，历史按原依据解释；若更正影响既有用户，需要另行制定通知和迁移方案，当前不自动改写用户数据。重新导入相同版本也不会恢复条目。更正时导入新版本、核验后撤下旧版。

公共目录属于共享内容，不因某个账号注销而删除；其个人副本及日记随账号导出与注销处理。0.14.0 已完成生产备份恢复、MySQL 迁移与并发演练，见 [发布记录](releases/0.14.0.md)；首批真实目录仍未导入，微信真机验收仍待执行。后续新增表需另行迁移，不能沿用该次验收结论。
