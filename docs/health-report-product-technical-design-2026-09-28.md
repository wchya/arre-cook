# 健康饮食报告：产品与技术方案

日期：2026-09-28。状态：产品蓝图；P1 可信习惯周报、P2a 个人包装标签计算和 P2b 周期比较、无需加热的混合配方已实施；标准食物目录、标准份量、自愿版本化档案和文字记餐草稿基础能力已实现。真实目录内容、烹饪配方、个性化摄入目标与照片录入仍为后续阶段。进度与验收见 [实施计划](health-report-implementation-plan.md)。

## 1. 产品决策

将 arre-cook 从“帮我选菜”扩展为“知道我最近怎么吃，并帮助我安排下一餐”。核心闭环：记录实际饮食 → 看懂本周情况 → 选择一个改善行动 → 加入菜单与采购 → 下周复盘。

首期服务日常饮食管理的成年人，优先解决家庭做饭、上班外食、希望饮食更均衡的场景。体重管理为可选目标；疾病营养治疗、孕产妇和未成年人专用摄入目标需要独立专业规则，不纳入通用自动目标。

核心价值指标是“看完报告后采纳行动，并在后续实际饮食中完成”，不是生成报告次数。计划采纳与实际完成分别统计。

## 3. 当前项目基础与缺口

已存在：Go/Gin/GORM、MySQL、React、原生微信小程序、个人数据隔离、家庭菜单、购物清单、AI 工具注册表、额度与并发保护。

健康报告入口已具备：

- `backend/internal/services/health_service.go`：`BuildHealthReport` 合并 `MealRecord` 与 `FoodJournalEntry`，统计 7/30 天记录、菜系和手动食物类别，并推荐换口味菜谱。
- `frontend/src/pages/Health.tsx` 与 `miniprogram/pages/diary/diary.js`：日记和报告入口。
- `backend/internal/agent/health_tools.go`：`get_health_report` 等工具。
- `backend/internal/models/dish.go`：菜谱食材/调料为 JSON 文本，缺少标准食物映射与营养计算结构。

关键缺口：

1. 记录条目不等于餐数；两种来源可能重复记录同一食物。
2. 没有统一的实际摄入份量、生熟状态、可食部、用油调料数据。
3. 没有标准食物营养库、计算版本和可信度来源。
4. “有记录的一天”不等于“当天完整记录”；不能据此计算全天不足。
5. 当前推荐主要基于偏好、近期记录与菜系变化，不能宣称营养缺口匹配。
6. 尚无独立的版本化健康档案、摄入目标、报告快照及改善行动反馈模型。

因此，应演进现有报告，不另建一套健康应用。

## 4. 用户流程与页面

### 4.1 渐进建立档案

初次只问目标（均衡饮食/体重管理/规律吃饭）、过敏与忌口、常见就餐方式。身高、年龄、体重、活动水平等在用户启用个性化营养目标时补充，并说明用途；跳过仍可使用习惯报告。

过敏、口味不喜欢、宗教/生活方式禁忌分开存储。过敏与禁忌是硬约束，喜好是排序条件。模型提取的新档案信息展示差异后确认，不静默覆盖。

### 4.2 记录一餐

四种入口：已有菜谱“吃过了”、最近吃过一键复用、文字描述、后续拍照。

确认卡包含：时间/餐次、食物列表、个人实际份量、做法、估算提示。默认提供半碗/一碗/一个/克等便捷单位，允许只记食物、暂不记份量。支持饮料、零食、外卖、自制混合菜与剩余未吃部分。

例如“中午吃了番茄鸡蛋和半碗米饭”，解析为同一餐的两项食物；番茄鸡蛋份量未知时不补造精确热量。家庭一盘菜必须记录“我吃了多少”，不能按整盘或默认平均分摊。

日末可选择“今天已记录完整”；漏记、明确未吃、已吃但份量未知分别表示。重复来源先提示关联/合并，不仅凭日期和名称自动删除。

### 4.3 报告页面顺序

| 区块 | 内容 | 可执行操作 |
| --- | --- | --- |
| 数据说明 | 时间范围、有记录天数、完整记录天数、份量/营养覆盖情况 | 补记、纠错 |
| 本期摘要 | 一项做得好的习惯、一项值得留意的情况；最多三条 | 查看依据 |
| 饮食结构 | 食物类别出现天数/餐数；数据充分后展示重量或份数 | 看相关餐次 |
| 营养情况 | 有依据时展示能量、蛋白质、脂肪、碳水、膳食纤维；钠按数据覆盖解锁 | 看来源与估算原因 |
| 趋势 | 可比口径的前后周期、可选体重趋势 | 切换周期 |
| 下一步行动 | 最多三项，默认突出一项，用户可换选 | 加入菜单、生成清单 |
| 方法与来源 | 指标定义、来源、规则版本、估算范围 | 反馈错误 |

日报定位为简短回顾；周报是主产品；30 天用于趋势和目标复盘。首页展示最新周报摘要，“我的”保留完整入口。小程序优先原生组件，Web 可增加详细趋势；两端共享统计口径和操作。

首版使用食物类别横条、记录日历、简单趋势线。缺数据处留空并写“未记录”，不画为零。食物种类出现次数不能画成摄入重量占比。避免将不可比维度拼成具有医学意味的雷达图。

### 4.4 报告示例（虚构演示数据）

> 9 月 21 日—27 日，共 5 天有记录，其中 3 天确认完整。
>
> 已记录的餐食中，有 4 天包含蔬菜；早餐信息仍不足，暂不评价早餐规律。
>
> 本周先做一件事：选择两天给早餐搭配一种自己能接受的蛋白质食物。
>
> 可选：鸡蛋、豆制品等，按本人忌口过滤。［选两天加入菜单］［换一项行动］

即使有完整记录，营养数据缺失仍需单独判断。不能从这个示例推断营养缺乏、热量不足或疾病风险。

### 4.5 报告到行动的闭环

行动卡绑定证据、食谱筛选条件和待安排餐次；用户确认后写入现有周菜单，复用买菜清单合并逻辑。下周区分“已计划”“用户标记完成”“实际记录支持完成”。

规则示例：记录显示食物搭配单一 → 推荐可补充的食物类别 → 从现有菜谱中找符合忌口、时间、预算与库存的候选 → 用户选择。候选不足时明确提示，不为了凑数突破禁忌。

现有种子菜谱集中于南方菜系、辣味与午晚餐，需要补充早餐、主食、蔬菜、豆制品、清淡烹饪和快捷餐。菜谱内容建设应与代码开发一起排期。

## 5. 指标与可信度规则

### 5.1 不使用黑盒健康总分

首版分别展示记录完整度、食物多样性和行动完成情况。若后续做“饮食习惯分”，必须公开公式、适用范围、缺失数据处理与版本，不能包装成身体健康程度。

每个指标都携带适用状态：可计算、仅局部观察、数据不足、不适用。建议初始产品门槛为周报至少 4 个完整记录日才展示全天营养均值及目标比较；这属于待试点校准的产品门槛，不是医学标准。份量和每项营养素的数据覆盖还需同时满足要求。

### 5.2 固定统计口径

- 餐数按餐事件统计，食物项数单列；同一天可以有多个加餐事件。
- 记录天数/周期天数是活跃覆盖；完整日由用户明确确认，不能由三条记录自动推断。
- 只对可计算且完整的日子求全天均值，展示样本数和不足信息；不能把漏记天当成零。
- 仅记录午餐时可以展示“已记录午餐摄入估算”，不能称“日均摄入”。
- 菜系用于口味偏好分析，不用于推断钠、油或健康程度。
- 前后周期统一规则版本、日类型和覆盖要求；样本不足时不显示升降结论。
- 体重与饮食同时变化只表述共现趋势，不推断因果。

### 5.3 来源与不确定性

区分营养成分来源与份量来源：食物库/包装标签/食谱计算/AI 估算；称重/标准份量换算/视觉估计/未知。用户确认食物名称不等于验证营养值。

营养值允许 null，不以 0 表示未知。当前报告通过 `portion_coverage` 分别返回称量/量取、标准份量估算、其他估算、仅文字份量和未知的去重食物项数；两端在数据说明中展示。总体结论不能比关键输入更确定。未经校准不展示“95% 置信度”；前端用“已称重”“标准份量估算”“份量待确认”等可理解标签。只有有依据的上下界才展示数值区间。

## 6. 技术架构

沿用模块化 Go 单体：双端 → Gin API/Agent 工具 → 记录服务、营养计算服务、报告聚合、行动计划 → MySQL；图片复用 Garage S3。

LLM 是解析与解释适配器：文字/照片生成结构化候选，经过校验和用户确认成为记录；报告统计由确定性代码生成，LLM 读取有界快照解释结果。无需首期引入微服务、向量数据库、自建 YOLO 或多智能体编排。

建议服务边界：

| 模块 | 职责 |
| --- | --- |
| MealService | 餐事件、实际摄入、来源关联、纠错与幂等 |
| FoodCatalogService | 标准食物、别名、单位、生熟状态、来源版本 |
| NutritionService | 食谱与实际份量计算、缺失标记、计算快照 |
| HealthProfileService | 自愿档案、目标、版本、适用人群 |
| ReportService | 周期聚合、证据、覆盖检查、报告版本 |

### 6.1 建议数据模型

原始材料只保留用户授权的必要内容与关联；支持删除与导出。历史计算快照用于解释报告，不凌驾于用户删除权。

### 6.2 营养计算

基本公式：实际摄入营养 = 同状态食物每 100g 营养 × 实际可食摄入克重 / 100。

复合菜按食材、调料、可食部与烹饪保留因素计算整道菜；如有成品总重量，再按个人食用成品比例分摊。生食材值与熟食重量不可直接相乘；无法可靠换算时要求补充或降级为估算。

整道菜混合不均、汤汁剩余、吸油量不确定必须可表达，不能用平均分摊冒充精确测量。预制食品优先用对应包装标签；同一道菜按配方计算与成品数据库匹配二选一，不能重复累加。

食物库优先覆盖中文常见食材、熟食与调料。候选数据包括具有合法授权的中国食物成分数据、USDA FoodData Central、包装标签与经核验补录；逐源核对许可、版本和生熟口径。本次未采购或验证数据授权。

营养目标另建版本化规则集，注明来源、适用人群与审核人。选择拟采用的中国居民膳食指南/膳食营养素参考摄入量等资料后完成专业复核；BMR 不等于每日摄入目标，不能复制参考项目 UI 中的简单乘数作为所有用户标准。

### 6.2.1 当前 P2a 的落地范围

实际新增 `nutrition_foods` 个人标签表，日记内嵌 JSON 营养快照，复用原记录与报告接口。标签 CRUD 位于 `/api/health/foods` 和 `/api/health/foods/:id`。标签来源固定为本人录入包装数据，保留版本、来源说明、g/ml、生熟状态；没有引入公共食物库。

计算版本 `label-per100-v1`：每 100 克/毫升数值乘以实际同单位份量除以 100，结果保留两位小数，空值不参与求和。六项营养素分别检查覆盖：7 天至少 4 日、30 天至少 18 日同时满足用户确认完整和全部食物项可计算，才显示该营养素日均。否则仅展示已知部分合计，不作缺口或达标判断。

Web 与小程序支持标签录入、修正、删除和 kJ 转 kcal。历史摄入快照不随标签版本变动；更新食物名称或自由文本份量时清除旧快照，需要重新计算。账号导出/注销包含标签与快照。上述实现不代表本章配方、标准库和目标蓝图均已交付。

### 6.2.2 当前周期比较

现有 `/api/health-report?days=7|30` 增量返回 `comparison`，包含前期日期范围、规则 `weekday-paired-v1` 和逐营养素结果。当前周期仍包含今天；前期紧邻且不重叠，两个周期使用同一次时间锚点和同一读取事务。前期计算跳过推荐与行动查询，避免重复生成推荐。

逐项取确认完整、每个食物项都有该营养值、计算版本为支持的 `label-per100-v1` 、`retained-mixture-v1` 或 `catalog-per100-v1` 的日期，按星期几匹配相同数量；有多余日期时优先取最近日期。匹配至少 4/18 对才返回两组配对日均和绝对差值。返回实际日期对以便双端追溯；由于样本不同，配对日均可能不同于本期全部完整日均。零值有效，不做百分比变化。补记、修改或删除造成完整确认失效后立即重新筛选。

比较仍包含个人标签误差和估计份量，不表示因果、达标或健康改善；不存在可比样本时返回空数值和数据不足原因。此项完成不代表标准库与配方目标已完成。

### 6.2.3 无需加热的个人混合配方

混合配方复用 `nutrition_foods`，`source=retained_mixture`，新增可空 `recipe` JSON：成品重量、方法、逐原料标签与版本快照、完整营养总量。`POST /api/health/recipes` 创建，`PUT /api/health/recipes/:id` 检查配方版本后修改；读取/删除沿用食物接口。个人标签和配方共最多300项，每配方2–20种不重复原料，不允许嵌套配方。

目前只接受用户确认 `unheated_all_retained`：无需加热且固体、液体全部保留，所有调料均已录入。原料必须匹配本人标签或已采纳标准食物的单位、状态与版本；成品重量0.01–10000g，全克重原料与成品合计需在5%或1g误差内。克/毫升不自动换算；部分体积原料须另称量整份成品。

整份营养按原料每100单位值乘以用量后求和，某项只要任一原料未知，整份该项即未知。摄入按整份总营养 × 个人成品克重 / 整份成品克重计算，不用四舍五入后的每100g展示值反推。食用量不能超过本批成品重量，均匀混合分摊一律标为估算，版本 `retained-mixture-v1`。历史日记嵌入配方与原料来源，标签/配方修改或删除不重写历史；同请求键重试先返回已提交记录，不因来源已删除而失败。

该范围用于直接混合食品，不从现有菜谱文本自动生成营养配方，不处理煎炒、吸油、弃汤或烹饪损失。比较支持当前包装标签和混合配方计算版本；其他未知版本仍排除。平台没有核验本人转录的营养数值。

### 6.2.4 标准食物目录基础能力

公共 `nutrition_catalog_foods` 保存不可变来源版本、名称/别名、生熟状态、每100g/ml可食部分营养与许可/核验信息。离线文件校验后显式事务导入，不预装未经核验的真实内容。登录用户搜索并采纳为个人只读副本，支持直接记餐与无需加热混合配方；逐层快照保留原版本依据，直接计算版本为 `catalog-per100-v1`。

撤下只阻止搜索与新采纳，不删除既有副本和历史；来源修正需新版本。目录可选提供有来源的标准碗/个份量：按同状态可食部分的基准单位换算，服务端固定标为估算，并在历史快照保留数量、系数和依据。没有核验份量时仅支持克/毫升，混合配方原料仍需填写实际克重/毫升。该范围尚未覆盖可食比例、生熟/密度换算或专业营养目标。接口、文件字段、部署与撤下说明见 [标准食物目录](nutrition-catalog.md)。

### 6.2.5 自愿健康档案基础

`health_profiles` 保存本人确认的目标意愿、常见就餐方式、过敏食材与生活方式/宗教禁忌食材；`health_profile_versions` 保留每次确认的内容与时间。目标意愿目前只有均衡饮食、体重管理和规律吃饭，可不选；不采集身体指标，不生成每日摄入目标。专业审核目标规则仍未交付。

档案独立于可供 AI 使用的旧饮食偏好，不自动复制或覆盖旧字段。个人登录态的 `GET/PUT/DELETE /api/health/profile` 提供读取、本人确认保存、清除内容及历史；带版本检查，冲突返回409。清除后仅保留无内容的递增版本号，防止旧页面重新提交恢复已清除内容。版本快照与当前内容、菜单缓存失效在同一账号事务锁下更新，加入账号导出/注销。

新增过敏与禁忌在统一推荐、明日推荐、个人周菜单及健康报告计划中作为硬约束，候选不足不放宽；健康报告还保留旧偏好的忌口过滤，与计划采纳一致。读取失败不跳过约束。手动查看/记餐不受此过滤，家庭菜单不自动应用成员的私密档案。匹配沿用菜谱食材等文本，不推断过敏原同义词、交叉接触或完整配料，仍需本人核对。

双端在饮食记录页提供可收起表单，修改后需重新确认；保存失败保留输入，版本冲突由本人选择重载，账号切换/关闭后的迟到响应丢弃。旧 Agent 令牌及嵌入会话无档案接口权限，旧偏好、画像和导出接口不附带档案内容。详见 [档案接口与边界](health-profile.md)。

### 6.2.6 主餐状态、早餐计划与首页摘要

2026-09-29 工作区补充：`health_meal_omissions` 以账号/日期/餐次为复合主键，存放本人确认的未吃声明。逐日投影展示 `unknown`、`recorded`、`not_eaten`；实际记录优先。写入检查当天完整指纹并使用账号事务锁，补记同一餐时清除声明；声明变更使全天完整确认失效。没有声明时保留旧指纹算法，不让迁移批量失效旧确认。

明确未吃不计进餐、食物项或零营养；只有声明而无实际食物的日子仍不能确认全天完整。早餐扩展现有计划与菜谱记餐接口，仅显式采纳，不自动生成随机早餐。报告可另行确认当天或过去的实际食用，撤销计划保留实际记录及其采购项。

`GET /api/health/summary` 复用七天报告聚合，省略上一周期、推荐及模型调用。双端首页展示实际记录覆盖与周报入口；账号切换丢弃旧响应，报告写操作409后刷新。接口与迁移边界见 [餐次状态与首页摘要](health-meal-status.md)，0.15.0 发布验收见[发布记录](releases/0.15.0.md)。

### 6.3 AI 处理流程

1. 识别输入意图，解析 food_name、portion、unit、meal_time 等候选。
2. 服务端匹配标准食物，校验 Schema、单位和范围；歧义返回候选或补问。
3. 展示可修改确认卡，保存时由服务端计算；未知可保留，禁止强制补数。
4. 报告先生成 metrics、coverage、evidence、rule_results、allowed_actions。
5. 模型仅输出引用这些证据的结构化叙述，禁止新增未提供数值、疾病诊断或食谱ID。
6. 服务端核验引用与数值，失败则回退规则模板；模型停用时仍可读报告、记餐、安排菜单。

复用现有 AI 服务端配置、额度、并发、内容校验和审计。健康解释范围需要同步调整现有仅围绕食谱的助手边界。营养档案不因加入家庭自动共享；外部 Agent 的新健康数据读取使用显式新 scope，旧令牌不自动获得。

### 6.3.1 当前文字草稿基础

本轮工作区已实现文字整理与确认入口：最长1000字、最多12项，模型仅摘取原文名称、个人份量及证据，不推导日期、餐次、营养或标准食物ID。严格JSON、原文匹配与模型语义核对后返回，双端可修改/移除，显式选择日期餐次并核对后才写入日记。无需模型即可继续手动记餐。

解析为限时40秒的同步请求，不存原文或未确认草稿；复用AI租约与独立长请求池。个人每日10次独立记餐额度与全站AI预算原子扣减，不占个人聊天额度。确认通过 `health_journal_batches` 保存幂等收据，与日记、未吃声明清除一起事务提交。账号注销删除新计数和收据。后续工作区已增加本人食物/公共目录候选查询与明确选择，用量仍由本人另填；没有已核验的真实公共目录内容。详情及未完成事项见 [文字记餐草稿](health-meal-drafts.md)。这不代表照片、自动份量推断、报告解释或后台作业已交付；真实模型评测仍待执行。

### 6.5 任务、缓存与资源

规则聚合先同步实现，以真实数据量测试响应目标；AI 解释和周期快照使用 MySQL 作业表，单进程有界 worker，租约、超时、有限重试、失败状态和幂等唯一键齐备。首期无须 Redis/Kafka。

报告缓存键含 user_id、周期、timezone、输入revision、profile_version、rule_version、计算版本；叙述额外绑定 prompt/model 版本。记录修改/删除、档案与食物映射变化标记失效，避免重复消费 AI 额度或显示过期结论。

滚动 7 天报告与每周归档分开：归档采用明确自然周和用户时区。调度只通知选择订阅的用户，无数据不生成空洞长文；提醒通过现有站内信接入，外部推送另设订阅授权。

当前部署资源有限，视觉模型优先调用现有可配置远端适配器；本地重型推理须另做资源评估。报告按需计算并缓存，不让每次打开页面触发模型。新增任务预算与交互聊天预算分开核算，并受站点总预算约束。

### 6.6 迁移与兼容

先建立统一读取投影，再逐步统一写入。历史记录保留 source_type/source_id 追溯映射；同餐多个菜项归入同一餐事件，疑似跨来源重复只提示人工确认。旧记录无份量时标记未知，不批量伪造营养值。

迁移脚本可重复执行、分批处理、有对账；上线前备份并演练回滚。旧客户端写入通过事务适配到新模型，避免异步双写漂移。历史营养快照不得因用户编辑现有菜谱而悄悄变化；修正历史记录时生成新版本。

现有日记查询最多取 500 条，报告新聚合必须专用 SQL 或完整分页，不能复用有限列表当作全部记录。统一业务时区和日期边界，处理补记、跨午夜与周期最后一天。

## 7. 安全、质量与验收

健康数据按个人隔离；家庭管理员不能天然读取成员体重、病史或报告。报告分享默认关闭，开启时选字段、可撤销且链接有期限。日志避免记录档案和图片原文，模型上下文按当前任务最小化。

新表、快照、导出、作业、上传引用必须加入现有账号注销链路；删除数据后相关报告和模型缓存同步失效。备份保留周期与恢复后再次执行删除的策略需有记录。

验收重点：

- 同来源重复提交只产生一份摄入；同餐三道菜统计一餐三项；计划菜谱不计实际吃过。
- 生/熟、克/毫升、可食部、整菜/个人份量、油盐与包装份量计算有人工核算的黄金样本。
- 漏记不补零，未知营养不变零，少量样本不产生全天不足结论；明确没吃和漏记可区分。
- 餐记录或档案修改后报告失效，历史菜谱更新不改原摄入快照；AI 返回数值与统计不一致时降级。
- 各新增接口、作业查询和 Agent 工具验证跨用户拒绝；家庭共享边界、账号切换迟到响应有回归。
- 用户采纳一次行动只生成一次计划/清单；失败时事务整体回滚。
- Web 与微信在相同记录下指标一致；手机拍照、份量编辑、补记与空态真机验收。

AI 评测先建立约 100–200 个代表性用例，覆盖中餐混合菜、多人合餐、外食、含糖饮料、含糊份量、过敏禁忌与恶意提示。记录识别修正率、克重误差、错误确定性陈述、违规推荐和调用成本；图片不能标出可靠重量的案例必须保留为未知/估算。
