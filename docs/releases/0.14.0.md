## 数据迁移与隔离演练

先备份生产 `ninimenu` 数据库，再恢复到独立 MySQL 8 schema `arre_health_release_0140`。迁移后 40 张原有表行数一致，新增 `health_profiles`、`health_profile_versions`、`health_day_confirmations`、`health_plan_items`、`nutrition_foods` 和 `nutrition_catalog_foods`。见[副本迁移回执](0.14.0/rehearsal-summary.json)。

使用新镜像在仅绑定宿主回环地址的临时容器验证接口。临时容器使用独立 JWT 密钥，不挂载生产上传卷，不配置生产 S3、SMTP、模型或微信凭据；测试账号与写入仅存在于隔离 schema。验证通过：

- 两个同时提交相同版本的档案保存请求，一次成功、一次 409；并发保存/清除保持版本一致，清除历史后旧请求不能恢复档案。
- 双账号档案、日记和标签隔离；本人导出含版本快照，旧 Agent 会话访问档案返回 401。
- 虚构标签 200 kcal/100g × 75g = 150 kcal；零脂肪与未知纤维保持区别，标签更改/删除后历史摄入不变。
- 记餐重试幂等、完整日确认和新增记录后确认失效。
- 同账号档案保存与计划采纳串行生效，禁忌更新后旧计划不可用、新采纳被拒绝；计划重试、撤销及跨账号拒绝正常。
- 注销测试账号后健康表内容清理，原登录令牌失效。

第一次接口演练的直接 SQL 测试菜名因 MySQL CLI 默认 latin1 被错误编码；为演练脚本显式设置 utf8mb4 后重新验证通过，未改动应用代码。最终[接口演练回执](0.14.0/rehearsal-api.json)记录成功结果。临时 schema、专属授权、容器和临时环境文件均已删除，见[清理回执](0.14.0/cleanup.json)。

正式切换仅暂停食谱站 Nginx 入口，等待 90 秒排空后停止旧容器，再次备份数据库与图片，执行 `DB_AUTO_MIGRATE=true / DB_MIGRATE_ONLY=true` 的独立迁移。正式迁移前后 40 张原有表行数一致（用户 4、菜谱 644、日记 15、菜谱用餐记录 3）；六张新表均为空，没有推断或自动创建个人健康档案，也没有导入模拟标准食物。见[正式迁移回执](0.14.0/migration-result.json)。
