## 二、架构设计要点（已落地到后端）

### 1. 账号与认证
- 登录：**邮箱验证码**（6 位、10 分钟有效、一次性、错 5 次作废、同邮箱 60 秒冷却 / 每小时 6 次、同 IP 每小时 20 次；验证码只存 SHA-256 摘要）。
- 未注册邮箱自动建号；`ADMIN_EMAIL` 对应的邮箱登录即为管理员。
- 兜底：管理员账号 `ADMIN_USERNAME` + `ADMIN_PASSWORD` 密码登录（PBKDF2-SHA512 21 万次，仅标准库）。
- 微信小程序：`wx.login` code → openid；已绑定直接登录，未绑定则引导邮箱验证码登录并**顺带绑定**（一个人一个账号，数据不分裂）。
- JWT（HS256，默认 30 天）+ `token_version`：改密 / 退出所有设备 / 禁用账号即时失效。
- 登录接口按 IP 限流；可选 `EMAIL_DOMAINS` 白名单（如只允许 qq.com、foxmail.com）。

### 2. 数据隔离
- 所有个人数据表都有 `user_id`，查询统一走 `database.OwnedBy(uid)`；菜品走 `database.VisibleDishes(uid)`（公共 + 本人私有）。
- 收藏 / 每日评价 / 家中库存因旧表有全局唯一约束，换成新表：`user_favorites`、`user_day_ratings`、`user_home_inventories`。
- **旧数据自动迁移**：首次启动把单用户时代的数据全部归属到初始管理员账号（只执行一次，旧表保留备查）。
- 注销账号会删除全部个人数据；支持一键导出本人数据（JSON）。

### 3. AI / 智能体能力（核心）
- **统一工具注册表**（`internal/agent`，22 个工具）：一套定义同时驱动三种通道，每次调用做 scope 校验并写审计日志。
  - 读：`get_context`、`get_taste_profile`、`get_preferences`、`search_dishes`、`get_dish`、`recommend_dishes`、`list_meal_records`、`list_favorites`、`get_week_plan`、`get_shopping_list`、`get_stats`、`list_behavior_events`、`list_suggestions`、`get_day_ratings`
  - 写：`log_meal`、`rate_meal`、`delete_meal_record`、`set_favorite`、`update_preferences`、`regenerate_week_plan`、`log_feedback`、`create_suggestion`
- **三种接入通道**
  1. 站内 AI 助手：`POST /api/assistant/chat`（SSE 流式），默认 DeepSeek（OpenAI 兼容，可换通义/Kimi/智谱等）；未配置模型时自动退化为本地推荐引擎，依旧可用。对话历史按用户保存。
  2. MCP：`POST /mcp`（Streamable HTTP、JSON-RPC 2.0、无状态），支持 tools / resources / prompts（今晚吃什么、规划一周、饮食报告）。**Hermes、Claude、Cursor、Cherry Studio 等配置 URL + Bearer 令牌即可接入。**
  3. REST 函数调用：`GET /api/agent/tools`（OpenAI/DeepSeek function calling 格式）+ `POST /api/agent/tools/{name}`；`GET /api/agent/openapi.json`（OpenAPI 3.1，可导入 GPTs Actions / Dify / Coze）。
- **凭证类型**（全部只代表某一个用户）
  - 个人访问令牌 `nm_…`：用户在「我的 → AI 连接」创建，只显示一次、库里只存摘要，可设有效期、随时撤销。
  - 嵌入会话令牌：App 给内嵌 iframe 智能体签发的 2 小时短期令牌（postMessage 交付）。
  - 权限预设：`readonly`（只读）、`advisor`（只读 + 推送建议 + 写反馈）、`full`（全部）。
  - 每个令牌每分钟限流（默认 120 次）；所有智能体调用写入审计日志，用户可查看。
- **推荐闭环：AI 建议收件箱**：外部智能体不直接改用户数据，而是 `create_suggestion` 推送建议；用户在 App 一键采纳（自动记入对应餐次）或忽略，结果回流为行为事件，供智能体评估推荐效果。
- **推荐引擎升级**：按用户画像打分；新增显式偏好（忌口、过敏原硬过滤且永不放宽、辣度、做饭时长上限、饮食目标、就餐人数），近 30 天“不想吃”降权，私房菜加权。

### 4. 图片存储
- 配置了 `S3_ACCESS_KEY/S3_SECRET_KEY` 时写入博客站 Garage（自实现 SigV4，无第三方 SDK，已用 AWS 官方签名样例验证）；否则写本地 `UPLOAD_DIR`。
- 对象键：`cook/u/<用户ID>/<年>/<月>/<日>/<时间戳-随机>.jpg`；普通用户只能删除自己目录下的图片。
- 读取：`GET /uploads/*` 先找本地（种子菜品图、历史上传），找不到再回源 S3，长期强缓存；也可设 `S3_PUBLIC_URL=https://arrebyte.top/uploads/` 直接走博客站 Nginx。
- 上传改为内容嗅探校验类型（不信任扩展名），压缩为 JPG 后存储。

已被测试覆盖的关键保证：
- 用户 A 的私房菜 / 记录 / 收藏 / 建议 / 审计日志 / AI 会话，用户 B 均不可见、不可改；普通用户不能改公共菜谱、不能进管理接口。
- 只读令牌看不到也调不动写入工具（REST 与 MCP 均验证）；令牌不能冒充用户登录态；撤销后立即失效。
- 单独授权 `dishes:read` 时不可调用会暴露口味画像摘要的个性化推荐；该能力需要 `dishes:read` 和 `profile:read`。
- `get_context` 的当日用餐上下文需要 `records:read`；外部 Agent 不能通过旧 REST 参数关闭用户的饮食偏好过滤。
- 顾问令牌推送建议 → 只有本人可见 → 采纳后自动生成用餐记录。
- MCP：initialize / 通知 202 / tools/list 按权限过滤 / tools/call 返回本人数据 / 越权返回 isError。
- 未配置大模型时 AI 助手 SSE 流式降级可用；过敏原永不出现在推荐里。
- 邮箱验证码一次性、错 5 次作废、冷却、域名白名单、管理员邮箱。
