# 健康饮食报告实施计划

依据：[产品与技术方案](health-report-product-technical-design-2026-09-28.md)。开始日期：2026-09-28。

## 交付顺序

采用分阶段可用交付，先完成 P1，再交付基于个人包装标签的 P2a，随后推进标准食物与配方的 P2b。工作区现有账号、主题等修改保留；不在本任务中发布生产。

### P2b：标准食物、配方与个性化目标（部分实施）

- [ ] 确认营养数据授权、版本、首批中文食物映射和人工核验负责人。
- [ ] 标准食物、别名、单位、生熟状态、可食部和每 100g 营养模型。
  - [x] 可核验目录基础能力（[内容与操作说明](nutrition-catalog.md)）：离线JSON校验/事务导入、来源版本不可变、别名搜索、个人引用快照、撤下后禁止新采纳。
  - [x] 可选核验标准份量：同状态可食部分系数、双端数量录入、服务端换算、估算属性和历史依据。
  - 仅接受明确每100g/ml可食部分的数据；不推断去皮/去骨比例、生熟或质量体积换算。
  - 导入需提供来源链接、许可说明、核验人和核验日期；默认只校验，显式应用后才写入。首批真实内容仍待人工核验，不预装模拟数据。
- [ ] 配方产量、烹饪因素和个人食用比例，保留缺失/估算属性。
  - [x] 无需加热、全部原料保留的混合配方；复用个人营养食物表，保存逐原料标签版本快照、成品克重与完整营养总量。
  - 原料支持本人包装标签及已采纳的标准食物，拒绝嵌套配方；原料量必须与来源单位、状态一致，录入时检查个人食物版本。
  - 按个人成品克重 / 整份成品克重分摊；任一原料缺少某营养素，该配方营养素保持未知。
  - 配方和食用量均明确为均匀混合分摊估算；加热、弃汤、吸油、未计原料不适用，后续单独建设烹饪保留数据。
- [ ] 自愿档案与版本化目标，专业审核适用范围及阈值。
  - [x] 本人确认的版本化档案：目标意愿、就餐方式、过敏与生活方式禁忌分离，双端填写、版本冲突及清除历史。
  - [x] 独立个人权限、旧 Agent 不自动获取；接入个人推荐/周菜单/报告计划硬约束及导出注销。
  - 不采集身体指标、不推导摄入目标；自动目标所需的适用人群与专业审核规则仍待确认。
- [x] 可比周期趋势与人工核算黄金样本。
  - 当前周期仍含今天，前一周期为紧邻且不重叠的 7/30 天；在同一数据库读取事务内生成。
  - 逐营养素筛选确认完整、全部食物项有值且使用当前计算版本的日期。
  - 按星期几匹配同等数量样本，同类优先选最近日期；周至少 4 对、30 天至少 18 对。
  - 展示两个周期、样本日期、配对日均与绝对差值；不计算零分母百分比，不把升降解释为健康改善。
  - 双端展示数据不足原因；补记或撤销完整确认后重新计算。

## P1 实现约束

新增表控制在每日确认与个人报告计划；扩展现有日记字段，避免重复建设摄入数据库。完整度用当天摄入指纹确认，任何来源的新增、删除、编辑均使旧确认自然失效，不依赖每个入口分别维护失效状态。

计划独立于随机周菜单缓存，读取菜单时叠加已采纳项，重新生成随机菜单不会丢失用户计划。买菜项沿用现有模型；撤销只清理本行动拥有且无实际记录/其他计划需要的项。

P1 不从菜系推测热量、油盐或营养缺口。P2a 只计算本人录入包装标签所支持的营养值，不提供个性化目标。标签未经平台核验，估计份量不等于称重。

## 上线与回滚

1. 按部署文档备份数据库，在预发布环境通过现有独立迁移工具运行 `SchemaModels`：需包含 `health_profiles`、`health_profile_versions`；此前阶段新增 `health_day_confirmations`、`health_plan_items`、`nutrition_foods`（含可空 `recipe` JSON 列），扩展 `food_journal_entries`（包括可空 JSON 营养快照）。旧数据字段为空，两个可空关联/请求键的联合唯一索引不合并旧记录。
2. 用两个账号验收记录与报告隔离、同一餐重复关联、完整度重新确认、计划采纳/撤销和买菜条目；核对账号导出/注销。
3. 配方新增 `/api/health/recipes`、`/api/health/recipes/:id` 写入口；读取和删除沿用 `/api/health/foods`。旧标签数据的 `recipe` 为空；原料快照随个人食品及日记包含在账号导出/注销中。
4. 标准目录新增 `nutrition_catalog_foods`，个人食物增加 `catalog_id`、`catalog`；目录及个人食物还需可空 `portions` JSON 列；须先执行应用模型迁移，不能只运行目录工具的表迁移。真实目录按核验文件显式导入；没有内容时两端显示空态。
5. 后端先上线，再更新 Web 和小程序。旧报告字段含义保留，新界面需要新后端返回扩展字段。
6. 回滚时优先关闭新入口并回滚客户端。新增档案后若回退到不支持其硬约束的后端，应先暂停相关个人推荐与计划写入，避免用户保存的禁忌被忽略；保留两张档案表。若回退旧后端，会忽略新计划表，且不具备新的采购去重与保留规则，因此应暂停新旧计划混合写入后再回退；保留新增表与字段，不执行破坏性降级迁移。
