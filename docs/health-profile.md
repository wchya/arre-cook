# 自愿健康档案

状态：基础档案及双端填写已实现，自动摄入目标尚未实现。依据 [健康饮食报告方案](health-report-product-technical-design-2026-09-28.md)。

## 接口与字段

三个接口仅接受本人用户登录态，不接受旧 Agent 令牌或 Agent 嵌入会话。客户端指定 `user_id` 不改变所属账号。

| 接口 | 行为 |
| --- | --- |
| `GET /api/health/profile` | 获取本人当前档案；未填写返回 `active=false`、`version=0` 和空字段，不创建数据 |
| `PUT /api/health/profile` | 本人确认后整体保存，提交当前 `version` 和 `confirmed=true`；返回递增版本 |
| `DELETE /api/health/profile?version=N` | 清除档案内容及所有历史，返回无内容的新版本；空档案用当前版本重复清除不再递增 |

PUT 示例：

```json
{
  "version": 0,
  "confirmed": true,
  "goal": "balanced",
  "eating_pattern": "mixed",
  "allergies": ["花生"],
  "dietary_exclusions": ["猪肉"]
}
```

- `goal`：空、`balanced`、`weight_management`、`regular_meals`，表示本人目标意愿。
- `eating_pattern`：空、`home`、`eating_out`、`mixed`，表示常见就餐方式。
- `allergies` / `dietary_exclusions`：各最多20项具体食材，每项1–40字，去首尾空白及大小写重复，拒绝空项、控制字符和超长项，不静默截断。数组为空表示未提供。
- 返回 `active`、`version`、`confirmed_at` 及上述内容。服务端生成确认时间，不由客户端指定。没有身高、体重、年龄、疾病或摄入阈值字段。
- 内容无效返回400；当前版本不同返回409；存储失败返回500，不向客户端透出数据库信息。409后先读取最新档案，由本人核对后再次确认，不自动覆盖。

## 数据与隐私

`health_profiles` 以 `user_id` 为主键；`health_profile_versions` 对 `user_id + version` 建唯一索引，保存每次确认的完整内容。两表通过 `SchemaModels` 迁移，旧用户不自动创建档案或从偏好推断健康信息。

保存、清除和健康报告计划采纳使用相同用户行锁。保存当前内容、写历史快照与清除周菜单缓存在同一事务完成。清除删除全部历史，当前行仅保留所属账号、递增版本和空字段，阻止旧页面在清除后把档案重新保存。账号注销删除这条版本行及全部历史。

本人 `/api/me/export` 返回 `health_profile` 和 `health_profile_versions`，这两个字段在同一读取事务中获取。既有 Agent 偏好、画像、报告和导出不增加档案内容，也不将它拼入模型上下文。以后若开放新健康数据给外部 Agent，需要另行设计授权 scope。

## 筛选边界

个人统一推荐、明日推荐、个人周菜单和健康报告计划使用档案中的过敏/禁忌作为硬排除项，不能被候选放宽或 `ignore_preferences` 绕过。报告推荐同时保留旧偏好忌口，与计划采纳的规则一致；候选不足返回少量或空结果。档案读取失败时返回错误或空菜单，不能继续使用无约束候选。

已保存的报告计划不会自动删除；读取时按当前食材与档案重新判断 `available`，有冲突就提示重新安排。记录实际吃过的食物不因忌口而禁止，历史摄入快照、完整日确认和营养统计不随档案改变。档案修改后报告下次读取立即重算推荐和计划可用状态，个人菜单缓存失效。

现有菜谱文本匹配不能证明完整过敏原覆盖，不展开同义词、过敏原家族或交叉接触。用户需填写具体食材并核对配料。家庭成员的档案不自动用于共享菜单；浏览菜谱、手动选择和实际记餐也不承诺自动排除。

目标与就餐方式当前只保存、展示及导出。版本化摄入目标、身体指标、目标比较仍依赖专业审核规则，不能把这一基础阶段当作个性化营养目标已交付。
