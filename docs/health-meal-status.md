# 餐次状态与首页摘要

2026-09-29 随 0.15.0 发布；生产迁移与验收见[发布记录](releases/0.15.0.md)。

## 个人接口

`PUT /api/health/days/:date/meals/:meal/status` 使用个人登录态。餐次为 `breakfast`、`lunch` 或 `dinner`，日期为今天或过去一年内的北京时间日期。请求必须包含：

```json
{"not_eaten":true,"fingerprint":"从当前报告对应日期取得的指纹"}
```

`false` 撤销未吃标记。账号从服务端身份获取，不接受请求指定账号。当天内容或声明已变化、或试图将已有实际记录的餐次改为未吃时返回409；双端刷新后重新核对。缺失字段、非法日期或餐次返回400。

报告每天的 `meals` 返回早/午/晚餐的状态：`unknown` 尚未记录、`recorded` 已有实际记录、`not_eaten` 明确未吃。`not_eaten_meals` 为周期内声明餐数；`meal_count`、`meal_event_count`、`item_count` 的原有含义保持不变。标记和撤销会取消当天完整确认。补记同餐时，同一事务清除声明；后续删除食物记录不会恢复它。

未吃不是食物，也不是零营养摄入。只有未吃声明的日子显示待确认状态，但不能确认全天完整或进入营养日均样本；至少需一条实际食物记录。这一版本不实现全天禁食的零摄入建模。

`GET /api/health/summary` 返回滚动七天的 `from/to`、`logged_days`、`complete_days`、`meal_event_count`、`item_count`、`not_eaten_meals` 和规则 `headline`。复用完整报告的数据投影，省略上一周期、推荐与模型调用，不保存报告快照。摘要不推导摄入目标或健康优劣。

## 早餐与计划

个人 `POST /api/health/plans` 接受早/午/晚餐；早餐采用现有计划与采购事务，重复采纳不重复生成。`GET /api/week-plan` 增加 `breakfast` 数组，仅展示显式早餐安排；无早餐可为空或 null，客户端兼容旧接口缺少该字段。随机菜单设置及家庭午晚餐不扩展。

报告“记为吃过”单独调用菜谱记录接口，先核对日期、餐次和食物，仅允许当天或过去且仍可用的计划。记录支持早餐，保留原采购幂等及取消计划不删实际记录的规则。现有周菜单批量记餐沿用其今明两天入口；未来记录仍排除在当前报告外。跨自然周计划先在报告中查看，周菜单进入对应周后显示。现有买菜页面继续展示今明两天。

Agent 的 `log_meal`、`list_meal_records` 和 `get_week_plan` 同步支持早餐实际记录与显式安排，早餐随机推荐与独立未吃写工具尚未提供。早餐菜谱内容需要后续补充。

## 迁移与验证

新表 `health_meal_omissions` 使用 `(user_id, meal_date, meal_type)` 复合主键及 `confirmed_at`。已注册 `SchemaModels`、独立迁移/复制、账号导出 `health_meal_omissions` 和注销清理。新增表为空；没有声明时指纹与旧版本相同，不改写旧食物记录和完整日确认。

0.15.0 已完成新备份、隔离生产副本迁移及账号并发演练，再运行正式独立迁移；API 继续保持 `DB_AUTO_MIGRATE=false`。回滚保留新表，暂停未吃及早餐写入口；旧后端无法清除补记对应的声明。

自动测试覆盖摘要一致性、隔离/导出/注销、冲突、事务回滚、实际写入清除、旧指纹、早餐计划/记录/采购生命周期及复合主键复制；双端验证确认与取消、账号切换、失败重试和状态显示。生产 MySQL 副本并发演练已通过；完整浏览器视觉和微信真机验收仍待执行。
